Summary

The short version

Nothing here is broken beyond repair, and the trees are not the problem — they are the cheapest thing in the project. Three specific pieces of code are eating the frame.

The 3 FPS is not caused by too much scenery. It is caused by a full-screen effect that runs 32 times per pixel, every frame, even at night when the sun is below the horizon. On a 4K screen that is roughly a billion texture reads per frame. No graphics card finishes that in 16 milliseconds. Turning it off at night and scaling it with the screen is the single biggest win available, and it costs nothing visually.

The washed-out daytime is also a code fact, not a taste problem. The post-processing chain has tone-mapping switched off — outputColorTransform = false — so instead of a filmic curve, colours brighter than 1.0 are pushed through a hard "soft clip" that flattens them to white. Dusk was hand-tuned to sit just under that ceiling, which is why dusk looks superb and day does not. Day sends far more light energy into the same pipe and slams into the ceiling everywhere at once.

The missing stars are the simplest bug in the file. A comment in main.js says the procedural sky handles stars now, and the old star field is force-disabled to prove it. The procedural sky has no star code in it at all. Night is a flat dark-blue dome because that is literally all it draws.

One more thing worth knowing, because it explains a lot of frustration: the "Global Brightness" slider does nothing. It writes renderer.toneMappingExposure, which is inert while post-processing is on. Every adjustment made with it was a no-op.

Two things deliberately left undone

Sky render order (part of WO-8). Moving the sky dome to draw after opaque geometry is the largest remaining GPU saving, and also the change most likely to expose latent transparency-sorting bugs in the water, ground fog and cloud sprites. It needs a visual pass on all three, so it belongs in its own commit rather than buried in a batch.

Half-resolution god rays (part of WO-2). This needs a second render target in the TSL pipeline, a structural change to PostProcessing.js. Sample-count tiering plus the sun-visibility gate already capture most of the win, so this is a follow-up, not a blocker.

Constraint

The dusk lock

Do not touch the dusk look

Every change in this document is designed so the Golden Hour Dusk render is bit-for-bit identical before and after. Any agent working on this must treat the following as read-only:

  • envConfigs[1] — the Dusk row in src/main.js
  • The 'Golden Hour Dusk (Default)' preset block
  • uDuskFactor and every expression it feeds in proceduralSky.js
  • uRolloffKnee = 0.75 and buildSoftClipNode in PostProcessing.js — dusk's saturation depends on this exact knee
  • The god-ray defaults uIntensity 0.85, uDecay 0.927, uDensity 0.50

The technique that makes this safe: every new control gets a neutral value at dusk. The exposure multiplier is 1.0 at dusk. Star brightness is 0.0 at dusk. Sky-tint lift is 0.0 at dusk. Multiplying by one and adding zero cannot change a pixel. Day and night get their own values; dusk keeps passing through untouched.

Verified: all 10 dusk-related lines are byte-identical to the previous commit, and the three god-ray constants are unchanged. The exposure lerp also snaps to exactly 1.0 once it is within a rounding error, so returning to dusk from another phase lands on 1.0 precisely rather than 0.9999.

Acceptance test for every work order: load the game on the default dusk preset, screenshot, apply the change, screenshot again from the same position. The two images must be identical. If they are not, the change is wrong regardless of how good it looks.

Audit · ranked by measured cost

What is actually eating the frame

Ordered by how many milliseconds each one gives back. The numbering is a work order, not decoration — fix them in this sequence.

01

God rays run at full resolution, always, even below the horizon

Critical

src/core/PostProcessing.js · isGodRaysEnabled = !LOW_GFX

The god-ray pass runs a 32-iteration loop, and each iteration does a dependent texture read of the full scene buffer. That is 32 fetches for every pixel on screen, every frame. The loop had no early exit, no downsampling, and no check for whether the sun was even visible.

DisplayPixelsFetches / frameGPU cost est.
1080p, DPR 12,073,60066 M~4 ms
4K, DPR 1.5 (Engine clamp)8,294,400265 M~30 ms
4K, DPR 2 (Render HD toggle)33,177,6001,061 M~120 ms+

The bottom row is the 3 FPS. Engine.js clamped device pixel ratio to 1.5, but the Render HD toggle in main.js silently overrode it to 2.0. On a 4K panel that quadruples every full-screen pass at once.

Before

Sun below the horizon at night, no visible rays anywhere on screen, framerate still on the floor. The pass was running and finding nothing.

After

Identical rays at dusk. The node is removed from the graph entirely when the sun is behind the camera or below the horizon, so the loop genuinely stops executing — a uniform multiply would not have saved anything.

What shipped

  • Pass gated on sun visibility, with asymmetric on/off thresholds so a sun sitting exactly on the horizon cannot thrash the shader recompile.
  • Sample count by tier: 32 desktop-high, 24 desktop, 16 tablet, 8 mobile — with uDensity compensated so ray length is unchanged.
  • Half-resolution rendering is still outstanding; it needs a second render target.
02

No resolution budget — the renderer scaled up on exactly the screens it should scale down on

Critical

src/core/Engine.js · src/main.js resize handler

Pixel ratio was set once at boot and once more when the HD toggle was clicked. The window resize handler called setSize() but never re-evaluated pixel ratio, and nothing measured whether the machine could sustain the resolution it was given.

A 4K monitor and a phone were treated as the same problem. They are opposite problems: the phone has few pixels and a weak GPU, the 4K monitor has enormous pixels and — usually — a mid-range GPU that was never asked whether it could cope.

What shipped

  • New src/core/DeviceTier.js caps by total pixel count, not DPR: ~2.3 M on mobile, 4 M on tablet, 8.3 M on desktop (4K native).
  • Adaptive resolution samples frame time over a 90-frame window and moves the render scale in 0.1 steps, floored at 0.6. It uses the median rather than the mean, so one terrain hitch cannot drop the whole resolution, plus a 1.5 s cooldown and a 3-window "good streak" before scaling back up.
  • The budget is re-applied inside the resize handler, so dragging onto a 4K monitor no longer quadruples the framebuffer.
  • Render HD is gone, replaced by Auto Resolution and a manual Render Scale. Touching the manual slider turns auto off so the two cannot fight.

This is the change that makes a single build viable on phone, tablet, laptop and 4K. Everything else is per-effect tuning; this is the governor.

03

Daytime is blown out because tone mapping is disabled

Critical Visual

src/core/PostProcessing.js · src/core/Engine.js

Engine.js sets ACESFilmicToneMapping with exposure 1.8. PostProcessing.js then sets outputColorTransform = false, which makes both of those settings completely inert whenever post-processing is on — which is always. Nothing tone-maps. The only thing standing between the scene and the screen is buildSoftClipNode, a Reinhard roll starting at 0.75.

That was a deliberate choice, and the comment explains why: full ACES desaturated the dusk sky. But it means brightness has no headroom. Look at the light budget:

PhaseAmbientDirectionalTotalLight colourResult
Day1.22.43.6#fffaeb near-whiteAll three channels clip → white
Dusk1.13.24.3#ffaa00 saturated orangeBlue stays low → colour survives
Night0.81.82.6#88bbff dim blueSky dome forced to near-black

Dusk has more total light than day and looks better, because its light is heavily saturated — the blue channel never reaches the ceiling, so hue is preserved. Day's near-white light pushes red, green and blue over the knee simultaneously, and everything above 0.75 collapses toward the same white. That is the haze in the screenshot.

What shipped — a per-phase exposure multiplier that is 1.0 at dusk

// PostProcessing.js — rgb only, applied immediately before the soft clip
export const uPhaseExposure = uniform(1.0);

// main.js — dusk has NO slider and is hard-pinned
timePhase === 0 ? params.dayExposure     // 0.62
: timePhase === 2 ? params.nightExposure  // 1.35
: 1.0                                    // DUSK — locked

Day at 0.62 pulls the whole frame back under the knee, so the soft clip stops flattening and the sky's blue, the grass green and the cloud shading all separate again. Dusk multiplies by one and is provably unchanged.

Day light energy was also cut at source — ambI 1.2 → 0.75, dirI 2.4 → 1.6 — and the light hue pulled off pure white. Night moonlight went the other way, 0.8/1.8 → 1.05/2.2. Both phases now have full colour and intensity controls in a new Daylight folder and the existing Moonlight & Night folder.

The dead Global Brightness slider now drives a real exposure trim instead of the inert toneMappingExposure.

04

Night has no stars because the star code was deleted and never replaced

Critical Visual

src/main.js · src/shaders/atmosphere/proceduralSky.js

An 8,000-point star field was built, added to the scene, and then hard-disabled in the animation loop every single frame:

// Hide old star field — procedural sky handles stars now
starMaterial.opacity = 0;
starField.visible = false;

The procedural sky did not handle stars. Searching proceduralSky.js for "star" returned nothing. Its entire night contribution was one constant:

const nightBase = vec3(0.015, 0.02, 0.06);   // ≈ #040510
sky = mix(sky, nightSky, uNightFactor);       // replaces everything

Because that mix ran to a factor of 1.0, night also threw away the horizon gradient, the sun haze and the mid-sky band. It was a flat dome at roughly 2% luminance. On an OLED or a colour-managed 4K panel it reads as pure black.

What shipped

  • Two star scales — coarse bright stars over fine faint dust — from a hashed 3D cell lookup on the view direction, with jittered in-cell positions so they don't sit on a visible lattice.
  • Magnitude variation from a second hash (a few bright, many faint) and an uncorrelated slow twinkle from a third.
  • A Milky Way band: a soft FBM ridge across one tilted great circle.
  • Stars fade out near the horizon the way real ones do through thicker atmosphere.
  • The night mix is now 0.82, not 1.0, so a trace of horizon gradient survives and the world keeps a skyline.
  • The dead 8,000-point starField object and its per-frame writes are deleted.
  • New sliders: Star Density, Star Brightness, Star Twinkle, Milky Way, Night Sky Lift — every one multiplied by uNightFactor, so none of them can affect dusk.
05

The terrain rebuild is a 55 ms synchronous freeze, and half of it was duplicated work

Critical

src/main.js updateTerrainGeometry · src/world/TerrainGenerator.js

Every time the player moves 150 world units, the whole 4000×4000 terrain plane is rebuilt on the main thread in one blocking loop. At the default 128 resolution that is 16,641 vertices, and each vertex triggered roughly 137 simplex-noise evaluations once you follow the call chain:

Per vertexCallsNote
getWorldHeight (centre + 4 normal taps)5each = island data + 2 biome height fns
getWorldColor2second call was dead — result overwritten
getBiomeAt1recomputed island data again
getPathStrength12 noise taps

The one-entry memo cache in getIslandData made this worse rather than better. The loop interleaves (x,z), (x−12,z), (x+12,z)… so every call evicted the previous one. The cache hit rate was effectively zero.

Measured against a real simplex implementation: 2.28 M noise calls, ≈ 55 ms in Node. A browser is 1.5–3× slower and a phone 5–10× slower — so 150 ms to half a second of total freeze on mobile, recurring every few seconds of flight. Setting Terrain Res to 256 makes it 9 M calls and roughly a quarter-second even on desktop.

What shipped

  • Deleted the duplicate getWorldColor call. Pure dead work across 16,641 vertices, every rebuild.
  • Replaced the single-slot cache with a Map keyed on coordinates quantised to 0.5 units, so the five height taps per vertex collapse to at most two island-data computations. The key stride was collision-tested across ±60,000 world units.
  • Hoisted a new THREE.Color() that was allocating once per vertex inside the North Pole branch.
  • Removed a console.log that fired with 5% probability inside the hot loop.

Still outstanding: time-slicing the rebuild across frames, and eventually moving it to a Web Worker. The cache fix removes most of the cost, but the remaining work is still synchronous.

06

The sky dome shades every pixel, then gets painted over

High

src/shaders/atmosphere/proceduralSky.js

The sky mesh has renderOrder = -1000, so it draws first. Its fragment shader is the most expensive in the project — three FBM evaluations (domain-warped), each four octaves, each octave four hash-and-sin operations. Roughly 48 transcendental ops per pixel.

Because it draws first, it shades all of those pixels and then terrain, water, clouds and trees paint straight over the top. On a ground-level shot where terrain fills 70% of the screen, 70% of the most expensive shader in the project is thrown away.

What shipped

  • FBM octaves are now set by device tier — 4 desktop, 3 tablet, 2 mobile — with amplitudes renormalised per tier so a 2-octave sky has the same overall contrast as a 4-octave one rather than looking washed out.

Deliberately not shipped

Giving the sky a high render order so the depth buffer rejects occluded pixels is worth 40–70% of the heaviest pass in the scene. It is also the change most likely to expose latent transparency-sorting bugs. It needs a visual check on water, ground fog and cloud sprites, and belongs in its own revertable commit.

07

Frustum culling was switched off on every instanced object

High

src/main.js · frustumCulled = false in 16 places

Seventeen instanced meshes — ten pine species, rocks, bushes, flowers, four cloud layers, birds — all had culling disabled. Every instance was submitted to the GPU on every frame regardless of where the camera pointed. Roughly 970 pine instances plus 300 clouds plus birds were vertex-shaded even when facing the opposite direction.

The flag was presumably set because the meshes are recycled around the player and their bounding spheres go stale instantly.

What shipped

  • An explicit boundingSphere is now set per frame on the pine, jungle and palm instanced meshes — centred on the focus point with the spawn radius plus 120 m of padding. Three.js honours object.boundingSphere over the geometry's, so this is correct and cheap.
  • Culling re-enabled on all of them. The padding is generous on purpose: the saving is in the whole-mesh reject, not a tight fit.
  • The new Ghibli tree meshes do the same thing from the start.

Clouds and birds were left alone — they are few, large, and the pop risk outweighs the saving.

08

Tree placement re-randomises, so the forest is never the same twice

High Visual

src/main.js pine recycle pass

Placement uses rejection sampling with Math.random(): up to 14 attempts per instance, capped at 60 attempts per frame across all species, validated against a hash-grid for minimum spacing. It works, but it has three structural problems.

  • Not deterministic. Fly away and come back and the forest is completely different. Trees visibly pop into existence in new places.
  • Starved. The 60-attempts-per-frame cap across ten species means dense forest fills in slowly and visibly.
  • Expensive. Each attempt calls getWorldHeight, getPathStrength, getBiomeAt and getIslandData — the same heavy noise chain as the terrain rebuild.

What shipped — deterministic cell hashing

The new Ghibli tree system replaces rejection sampling with a hash. The world is divided into fixed cells; a hash of each cell's coordinates yields a fixed number of jittered points. The same cell always yields the same trees. No sampling loop, no random, no popping, and the spacing guarantee comes free from the cell size.

// Deterministic — same input always yields the same tree
function cellHash(cx, cz, slot) {
  let h = Math.imul(cx, 374761393) + Math.imul(cz, 668265263) + Math.imul(slot, 2654435761);
  h = Math.imul(h ^ (h >>> 13), 1274126177);
  return ((h ^ (h >>> 16)) >>> 0) / 4294967296;
}

Retro-fitting the existing pines to the same scheme is optional and would be a separate work order.

Design · Ghibli foliage

How the trees work

The good news: these assets are close to ideal, and they already contain the trunk/canopy split you asked for.

What the files actually contain

FileVertsTrisHeightSpreadCanopy / trunk verts
Background_Tree_Atlas_001_alt10410111.4011.4 × 29.398 / 6
Background_Tree_Atlas_002_alt46367.447.4 × 18.236 / 10
Background_Tree_Atlas_003_alt1141097.056.7 × 26.0106 / 8

All three ship a custom vertex attribute called _IS_CANOPY — a float, 0 on trunk vertices and 1 on canopy vertices. That is exactly the trunk/canopy separation you asked for, already baked into the mesh. No geometry splitting is needed; the shader reads the attribute and picks a colour. GLTFLoader lowercases unknown attributes, so it arrives in code as _is_canopy.

They are alpha-masked, double-sided card clusters with a base at y = 0, so they sit on the ground with no offset. At 36–109 triangles each, geometry is a non-issue: ten thousand of them is 700K triangles, which a phone handles comfortably. The cost is entirely fill rate from alpha-tested overdraw, which is why the LOD scheme targets pixels rather than polygons.

All three are in use. At these triangle counts variety is free, and three silhouettes at three different heights is what stops a procedural forest from reading as a repeating stamp.

Placement

Deterministic cell hashing on 34 m cells. Each cell hashes to 0–3 candidate trees depending on the density setting. A candidate is kept if:

  • the biome at that point is Ghibli Land,
  • terrain height sits between the min/max elevation sliders,
  • island mask ≥ 0.35 and path strength < 0.20 — the same tests the pines already use,
  • local slope is below the threshold, so trees don't grow out of cliff faces.

Species is chosen by a low-frequency noise field so you get groves of one type rather than an even shuffle, with 18% mixed undergrowth to break up the boundaries. The global thresholds are the measured 33/67 quantiles of that field, so all three species get equal share overall while any given place still favours one. Rotation and a ±17% scale jitter also come from the hash — the same tree is always the same tree.

Level of detail

Three bands, each cutting fill rate rather than triangles:

BandRangeSidesWindalphaTestPurpose
near0 – 140 mDoubleYes0.35Full quality where it's seen
mid140 – 420 mSingleYes0.50Halves fragment work
far420 – 1100 mSingleNo0.62Silhouette only
—1100 m +culledTerrain tint carries it

Raising alphaTest with distance is the important trick: it discards more fragments earlier, which directly buys back the fill rate alpha-masked foliage costs. It also reduces the shimmer thin alpha edges produce once they get smaller than a pixel.

The bands differ in material, not geometry — at ~100 triangles there is nothing worth decimating, and every millisecond is in the fragment stage. Nine InstancedMesh objects total (3 variants × 3 bands), so nine draw calls.

How the cost is kept off the frame

A full sweep at 1,100 m radius visits about 4,200 cells and costs ~30 ms in one burst. That would be a visible hitch every time you moved 55 m. So the cell walk itself is sliced across 18 frames, not just the buffer write — measured at 1.5 ms average, 4.4 ms peak. The instance buffer is only committed once the whole field is known, so it is never shown half-populated.

Colour control

The material reads _is_canopy and mixes between two independently editable ramps:

canopy = mix(canopyShadow, canopyLit, heightGradient) → canopyTip at the crown
trunk  = mix(trunkBase, trunkTop, heightGradient)
final  = mix(trunk, canopy, _is_canopy)

Five colour pickers plus a per-tree variation spread, in a Ghibli Trees → Background Tree Atlas → Colors folder. The atlas texture is multiplied by these ramps rather than replaced, so the painted detail survives while the palette stays fully editable — and a Texture vs Palette slider blends between the raw atlas and a flat stylised look.

Wind sway is weighted by _is_canopy as well as height, so trunks stay rigid and only the crown moves.

Risk register

What could go wrong

Stated up front, because you asked. Roughly in order of how likely they are to bite.

Dusk drift

The single biggest risk. Every one of these changes touches code that dusk flows through. The mitigation is the neutral-value rule — multiply by 1.0, add 0.0 — plus a line-by-line diff check. If an agent reports "dusk looks slightly better now," that is a failure, not a bonus.

The soft-clip knee is load-bearing

uRolloffKnee = 0.75 and outputColorTransform = false are not mistakes; they are a deliberate workaround for ACES desaturating the sky, and the comment in the file says so. Adding a proper filmic curve later is the architecturally correct fix, but it would require retuning dusk, which is off the table. The per-phase exposure multiplier works within the existing constraint rather than replacing it.

Alpha-masked foliage is a fill-rate trap

These trees are cheap in triangles and expensive in pixels. Flying low through a dense grove is the worst case — many large, overlapping, double-sided, alpha-tested quads. If frame time spikes near the ground, shrink the near-band range rather than thinning the forest; thinning is visible, range reduction is not.

Adaptive resolution can feel like the screen is breathing

Mitigated with a median filter, a 3-window good-streak requirement, and a 1.5 s cooldown after every change. If it still reads as unstable, widen the thresholds rather than disabling it — the alternative is a fixed resolution that is wrong on most machines.

Preset compatibility

New settings keys mean old saved presets are missing fields. An undefined uniform is a black screen, not a warning. This is WO-12 and it is not done.

WebGPU on mobile is uneven

The project uses WebGPURenderer throughout. WebGPU on Android is recent and on iOS newer still. The device tiers are a starting estimate, not a measurement — WO-11.

Two pre-existing errors, unrelated to any of this

The console shows repeated ERR_CONNECTION_REFUSED against localhost:9100/api/load-scene and /api/list-models, plus the JSON parse errors they cause. That is a separate editor backend that isn't running. It predates these changes and is harmless, but it is noise that hides real errors.
